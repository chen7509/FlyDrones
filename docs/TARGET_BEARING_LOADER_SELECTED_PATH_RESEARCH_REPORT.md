## Pinned loader source explanation

The existing full untruncated glibc2.39 tree has20266 members at commit `ef321e23c20eebc6d6fb4044425c00e6df27b05f`. Six retained full source/license files were re-audited and four necessary source files fetched at that same commit: dl-object.c, canonicalize.c, POSIX dl-fileid.h and Linux dl-origin.c. All ten match retained Git tree sizes/blob IDs and independent SHA256. Full COPYING/COPYING.LIB and each file notice are retained. This is upstream source provenance, not signed authentication, the installed distribution's exact build/configuration, or a completed transitive license bill.

1. `_dl_dst_substitute` copies ordinary characters and substitutes `$ORIGIN` from the object's l_origin. The normal path decomposition trims trailing slashes and appends a slash; it does not globally collapse parent components. The normalization called for secure trusted-directory policy is a distinct conditional path, not authority to canonicalize every ordinary selected filename. [Pinned dl-load.c](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/elf/dl-load.c#L273).
2. `open_path` concatenates directory/capability/name, calls open_verify, and copies the successful buffer into realname. open_verify passes the name to read-only/CLOEXEC open (with possible auditing-name handling). Thus retained `../../` spelling is consistent with loader path construction; this source reasoning is not a new observation of the target kernel's actual walk. [Path search/open](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/elf/dl-load.c#L1790).
3. `_dl_new_object` assigns l_name from realname and, for a known shared-object name, copies that spelling then removes its filename to form l_origin. It does not generally realpath it in that block. Linux dl-origin.c's `/proc/self/exe` path is for obtaining the executable's origin when needed; it is not a rule that all shared-object origins become canonical. Hence even inode-equal aliases must retain load spelling/context. [Object origin](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/elf/dl-object.c#L181), [Linux executable origin](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/sysdeps/unix/sysv/linux/dl-origin.c#L32).
4. The ordinary trace formats l_name; it need not print a canonical path. File reuse separately obtains descriptor identity and compares loaded file IDs. The POSIX implementation uses fstat device/inode. Those fields identify a file within the relevant filesystem/namespace at an observation; they are not content/source/loader-context authentication. The actual distribution's selected header/configuration is not certified here. [Trace](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/elf/rtld.c#L2101), [descriptor identity](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/sysdeps/posix/dl-fileid.h#L20).
5. `canonicalize.c` processes components, reads links and inserts link targets ahead of the unprocessed suffix; a later `..` therefore acts after preceding symlink expansion. It also checks directory requirements for suffixes such as `/..`, instead of making a regular file's parent spelling valid by string manipulation. Conceptually, if `/fixture/link` points to `/other/nested`, `/fixture/link/../lib` can refer to `/other/lib`, not the lexical `/fixture/lib`; this is a source-derived example, not a newly measured filesystem fixture. [Component/link handling](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/stdlib/canonicalize.c#L233).

These distinctions explain why removing `..`, global guard relaxation or deduplicating solely by inode would lose evidence. RUNPATH inheritance, auditing behavior, already-loaded reuse and interpreter symbol scope are still separate context questions; this report does not claim a new complete runtime model.
