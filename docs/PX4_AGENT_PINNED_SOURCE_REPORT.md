# Pinned XRCE Agent build-input candidate

An independent **source-only** copy of the PX4-compatible Micro XRCE-DDS Agent v2.4.3 now fixes its five directly declared superbuild references to full observed Git object IDs. The copy is a candidate for a later bounded build. It does not prove that those remote objects have been fetched as commits, that their transitive dependencies are closed, that a binary can be built within this host's resources, or that PX4 and the Agent exchange data. No Agent, Docker, PX4, Gazebo, OpenVINS or trainer was started in this stage.

The [design](superpowers/specs/2026-10-10-pinned-xrce-agent-source-design.md) and [plan](superpowers/plans/2026-10-10-pinned-xrce-agent-source.md) use the Agent release/commit/tree from the [prior source-readiness report](PX4_AGENT_V243_SOURCE_READINESS_REPORT.md). [PX4 v1.17's uXRCE-DDS guide](https://docs.px4.io/v1.17/en/middleware/uxrce_dds) names Agent v2.4.3 for its v2-family client; the [upstream v2.4.3 release](https://github.com/eProsima/Micro-XRCE-DDS-Agent/releases/tag/v2.4.3) is Apache-2.0. The project still uses the upstream default Fast/CED/discovery/P2P/CAN/logger feature options. This avoids silently shrinking the Agent merely to fit current memory. The only source transformation is one occurrence each of `UAGENT_P2P_CLIENT_TAG`, `_fastcdr_tag`, `_fastdds_tag`, `_foonathan_memory_tag` and `_spdlog_tag` in `CMakeLists.txt`, from the upstream tag/branch text to the five exact objects recorded in the spec. The unmodified `cmake/SuperBuild.cmake` consumes those variables. The frozen default superbuild still has other build-system and runtime dependencies that have not been audited to closure.

The first real preparation refused before creating `source-v1`: previous source research had hashed Windows checkout files. `core.autocrlf=true` plus upstream `.gitattributes text=auto` gave `CMakeLists.txt` SHA-256 `00e2f8c6…` in the checkout but `99a49347…` for the Git blob. The previous evidence archive remains an accurate checkout snapshot and was not rewritten. A new regression test failed on the checkout-hash constants, then the preparer was corrected to bind the five **raw Git blob** hashes; 23 initial focused/adjacent tests and changed-file Ruff passed. The failure is retained in `results/px4-agent-v243-pinned-source-dev-1701/prepare-console.txt` with no `source-v1` directory.

The second preparation wrote `source-v2`: Agent commit `73622810d984349b80bbac0ef55fc0b694d62222`, tree `30de05fce045d2cc40c3b911f4dc5085b24f1ab4`, 213 files, 4,067,926 original Git-blob bytes. `source-profile.json` SHA-256 is `a0fd774f81c43942f91cb07e52c166cf415643061f4ad4475ea50556ad9a04bc`; patched `CMakeLists.txt` SHA-256 is `8486b80e2b928f55d3dcd46e5f290bd762e210d4c8022f69bdad1abdd7e5d0bf`. The profile records every output file hash and original Git mode, but marks binary build, local dependency-commit verification, PX4 interoperability and owned-source-trial eligibility **false**. Windows staging does not establish Linux executable permissions or linked-library closure; a later build must verify both.

An independent review found that replacement refs and Windows pathname aliases were not yet excluded by the preparer. Five new RED cases reproduced those conditional defects; after the fixes, all 13 parameterized test cases passed. The preparer now disables Git replacement objects and rejects casefold aliases, Windows device/trailing-dot names and the reserved manifest path before writing. A fresh `source-v3` was produced with the corrected tool; its profile SHA-256 is the same `a0fd774f81c43942f91cb07e52c166cf415643061f4ad4475ea50556ad9a04bc` because the current 213-file upstream tree has no such collisions or replacement refs. Source-v2, source-v3 and the final source-v4 remain separate. The final source-v4 keeps the same profile hash and is independently checked in `audit-v4.json`; the new guard also rejects directory-case aliases such as `A/one` and `a/two`. The audit-v3 script independently read all 213 blobs with replacement refs disabled and found only the intended CMake change. The earlier review also found a manifest-field spelling mismatch in the design, now corrected.

An initial independent audit using `git archive` failed on `.dockerignore`: under the installed Windows Git attributes it exported CRLF, unlike the raw blob copied by the preparer. That failure and the 4,362,240-byte archive are retained, not relabeled a source mismatch. The corrected auditor used separate `git show HEAD:<path>` reads and checked all 213 raw blobs against `source-v2` (and a later separate v3 audit against `source-v3`), the five exact substitutions, the manifest hashes, file set and false qualification flags. Only `CMakeLists.txt` differs. `audit.json` records `reference_kind=git_show_raw_blob`, `source_file_count=213`, `changed_from_git=["CMakeLists.txt"]`; it does not reclassify the checkout/archive failures as successes.

Final verification after review: 83 focused and adjacent PX4 ROS2 source tests passed; changed-file Ruff and `git diff --check` passed. A mistaken first adjacent-test path produced a retained no-tests error before the corrected test run. The independent reviewer found a directory-case alias gap; a RED/GREEN test and fresh source-v4 preparation fixed it, and the source-v4 raw-blob audit passed. Evidence includes the full final candidate tree, all preparation attempts, the rejected archive audit and the corrected raw-blob audits; it does not include a built Agent.

Next, fetch the five **exact** objects into separate immutable source directories, verify each object type, tree, license, submodules and additional CMake fetches, then freeze a single-job compiler/link recipe and preflight resource budget. Only after a qualified binary exists should a prospective unarmed PX4/Agent/logger trial test UDP transport, process/clock identity, actual `vehicle_odometry` ULog samples and DDS-to-ULog agreement. Preserve the diagnostic logger's changed load and every failed study; do not use this candidate to publish ODOMETRY, adjust EKF2, arm a vehicle or admit training data.
