# Gazebo D3D12 五机稳定性单变量验证设计

## 1. 背景与目标

当前五机 PX4/Gazebo 无故障基线的任务完成数依次为 `1/5`、`5/5`、`5/5`、`4/5`、`5/5`、`4/5`，不能作为稳定基线。对齐后的性能采样表明，长 `/clock` 间隔中 Ogre、Mesa Gallium 和 Gazebo Sensors 调用栈明显富集；当前无显示 EGL 查询报告 `llvmpipe`，与 CPU 软件渲染方向一致。降低深度相机分辨率没有消除约 250–300 ms 的墙钟停顿，因此不能继续用单次成功或减少像素证明问题已解决。

本设计只验证一个因果假设：**在保持五机世界、相机、PX4、策略、安全门槛和试验顺序可比的前提下，把 Gazebo OGRE2 从软件渲染路径切换为 WSL Mesa D3D12 的 NVIDIA GPU 路径，能否消除稳定飞行期的视觉和仿真时钟尾部停顿，并使五机任务重复稳定通过。**

这项工作是现实 VIO 替换前的仿真基础设施稳定性修复。当前控制链仍转发 Gazebo 位姿真值；即使本设计全部通过，也不能称为真实相机与 IMU VIO、HITL 或实飞证据。

当前本机基线为 Gazebo Sim 8.15.0、`gz-rendering` 8.2.3、`gz-sensors` 8.2.2、Mesa 25.2.8 和 PX4 提交 `d6f12ad1c4f70ad3230afd7d86e971421e02fef4`。WSL 提供 `/dev/dxg`，没有 `/dev/dri`；宿主机同时有 Intel Iris Xe 与 NVIDIA GeForce RTX 3070 Ti Laptop GPU。因此适配器固定和实际后端证明都是试验有效性的必要条件。

## 2. 范围与非目标

### 范围

- 给现有 WSL PX4/Gazebo 五机入口增加显式、可审计的渲染配置档。
- 对请求的 D3D12/NVIDIA 路径做启动后证明，拒绝静默回退到 `llvmpipe`。
- 采用同世界、同配置的成对重复试验，比较当前默认路径和 D3D12 路径。
- 记录任务、安全、时延、实时率、资源占用和逐机 PX4 外部视觉融合证据。
- 在无故障稳定门槛通过后，重跑 120 ms 延迟和 400 ms 断流回归。

### 非目标

- 不改变 250 ms VIO 新鲜度门槛，不用放宽门槛掩盖停顿。
- 不降低相机分辨率或更新率，不改变物理步长、飞行速度、策略、世界或 PX4 参数。
- 不把 Gazebo 真值转发改称 VIO，也不开始实施真实 VIO 管线。
- 不引入 Xvfb、容器化 Gazebo、远程渲染服务器或新的仿真器。
- 不用本节结果推断 20、50 或 100 个物理实例的规模能力。

## 4. 冻结配置与唯一实验因素

正式比较前冻结以下内容，并把内容摘要写入每轮清单：

- Git 提交、PX4 提交、Gazebo/GZ/Mesa/WSL 版本。
- 五机世界、模型、相机 SDF、策略权重及其 SHA-256。
- 深度相机 `160×120 @ 10 Hz`、物理步长、速度限制和任务时限。
- 起点、目标、世界种子、策略种子和扰动种子；使用现有固定基线种子 `240901`。
- PX4 参数、GNSS 关闭时点、外部视觉接口、EKF2 配置和安全层参数。
- VIO 新鲜度门槛 250 ms，以及控制器、转发器和日志配置。

唯一实验因素为 `FLYDRONES_GZ_RENDER_PROFILE`：

- `default`：保持当前 OGRE2 自动无头和现有 Mesa 选择逻辑。
- `d3d12-nvidia`：仍使用 OGRE2 和相同无头入口，但为 Gazebo 进程注入 `GALLIUM_DRIVER=d3d12` 与 `MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA`。

这两个环境变量共同定义一个不可拆分的“渲染执行配置档”：前者选择 D3D12 Gallium，后者消除双 GPU 机器上的适配器不确定性。不得在同一轮再修改其他仿真或飞行参数。

## 5. 组件与数据流

### 5.1 启动配置

现有五机启动脚本解析渲染配置档。未知值、缺少 D3D12 Mesa 驱动或无法识别 NVIDIA 适配器时，在启动 PX4 和机队前失败。`default` 继续是默认值，避免改变其他测试入口。

渲染变量只传入 Gazebo 服务器及必要的后端证明命令，不污染 PX4、控制器或结果分析进程。脚本退出和异常路径继续清理自己启动的 PX4、Gazebo、桥接器和控制器，不终止无关进程。

### 5.2 后端证明与静默回退处理

D3D12 轮次只有同时满足以下条件才有效：

1. 清单记录请求的配置档及两项环境变量。
2. `eglinfo -B` 或等价只读查询报告 D3D12 和 NVIDIA 适配器，而非 `llvmpipe`。
3. Gazebo 服务器 PID 的 `/proc/<pid>/maps` 包含 D3D12/DXCore 库。
4. 深度相机实际发布消息，且分辨率和频率与冻结配置一致。

任一条件失败时停止该轮并标记 `renderer_attestation_failed`。不得自动改回 `default` 后仍把该轮计入 D3D12 样本。

### 5.3 运行清单

每轮清单至少包含：

- 轮次、配对号、执行顺序、开始/结束时间和退出原因。
- 仓库/PX4 提交与工作树状态。
- 世界、模型、相机、策略、PX4 参数和脚本的哈希。
- 所有随机种子与冻结参数。
- 请求和证明的渲染器、GPU 名称、Gazebo PID 和后端库证明摘要。
- 主机 CPU、GPU、内存、WSL、Mesa、Gazebo 和 PX4 版本。
- ULog、转发日志、时钟探针、资源探针、轨迹回放和摘要文件的路径与 SHA-256。

### 5.4 时延与资源观测

在每台机和全机队层面分别统计：

- 原始视觉回调墙钟间隔 p50、p95、p99、最大值和超过 100/200/250 ms 的次数。
- `/clock` 墙钟间隔 p50、p95、p99、最大值，以及每个长间隔推进的仿真时间。
- VIO 接收至发布延迟和控制器观察到的数据年龄。
- 实时率 RTF、Gazebo/PX4/控制器的 CPU 与 RSS。
- 可用时记录 GPU 利用率和显存；取不到时标记 `unavailable`，不得填零。

启动阶段和稳定飞行阶段分别汇总。启动异常仍计入任务可靠性和启动失败，不用“排除启动期”删除失败；稳定飞行延迟门槛从五台机均建立连续输入、PX4 状态健康且任务计时开始后的统一事件计算。

### 5.5 飞行与安全证据

每轮保存逐机任务接受/完成、集合、降落、碰撞、最小间距、围栏和控制器退出状态。ULog 必须逐机核对 GNSS 关闭后的外部视觉位置/速度融合、创新、估计器复位和失效保护状态。当前 Gazebo 位姿真值仍作为本阶段的外部视觉替身进入 PX4，同时也用于离线轨迹和安全距离核对；报告必须明确标为“真值替身”，不得称为真实 VIO。

## 6. 成对试验协议

先运行最小启动验证和单机烟雾测试；它们只验证接入，不计入五机稳定性样本。接入通过后冻结配置，不得在正式试验之间调参。

正式试验由五个配对、共十轮五机试验组成。每一对使用完全相同的冻结输入；为降低温度、缓存和时间顺序偏差，顺序固定为：

1. 配对 1：`default → d3d12-nvidia`
2. 配对 2：`d3d12-nvidia → default`
3. 配对 3：`default → d3d12-nvidia`
4. 配对 4：`d3d12-nvidia → default`
5. 配对 5：`default → d3d12-nvidia`

所有轮次均保留，包括启动失败、任务失败、门控、超时和异常退出。若中途发现代码或冻结配置必须修改，当前正式序列作废；修复后从新的提交重新执行完整十轮，不能只补失败轮次。

## 7. 验证矩阵

### 7.1 单元与静态测试

- 接受 `default` 和 `d3d12-nvidia`，拒绝未知配置档。
- 验证环境变量只传入预期进程。
- 模拟 renderer 查询失败、`llvmpipe`、错误 GPU、缺少 D3D12 库映射和无深度帧，均应拒绝试验。
- 清单必须包含冻结字段；缺字段或哈希变化时正式运行失败。
- 摘要器正确计算 p95、p99、最大值和阈值计数，并保留失败轮次。
- 运行现有相关 pytest、Ruff 和脚本静态检查，避免破坏默认入口。

### 7.2 正常与边界测试

- `default` 单机和 D3D12 单机均能启动、接收深度帧并安全降落。
- D3D12 五机启动验证确认五套 PX4、传感器、端口和日志相互独立。
- 同一配置重复运行不会复用旧 PID、端口、清单或 ULog。
- GPU 查询不可用时保存原因并使 D3D12 轮次无效，不影响 `default` 模式。
- 进程退出、超时和用户中断均清理本轮资源并保存已有证据。

### 7.3 故障注入与回归

无故障五机稳定门槛通过后才执行：

- 120 ms 延迟：不得触发 250 ms 新鲜度门控；验证任务、融合和日志连续性。
- 400 ms 断流：受影响车辆必须停止发送自主速度目标，并在阈值加一个控制周期和记录容差内进入既定降落路径；最后自主命令、检测与降落请求的时间线必须可复核。
- 故障轮按安全结果验收。按设计主动降落不冒充正常任务完成，也不因任务中止否定已证明的安全门控；未受影响车辆的结果单独报告。
- 完成全部现有 VIO 门控、PX4/Gazebo 单机和五机回归。

## 8. 通过门槛

D3D12 修复只有同时满足以下条件才通过：

1. 五个正式 D3D12 轮次的后端证明全部有效。
2. 五轮均达到 `5/5` 任务完成和 `5/5` 安全降落，即累计 `25/25`；零碰撞、零围栏越界、零安全距离违规。
3. 无故障轮没有 VIO 新鲜度门控，逐机 GNSS 关闭后的 PX4 外部视觉融合证据可核验，没有未解释的估计器复位或真值接管。
4. 稳定飞行阶段原始视觉流和 `/clock` 的最大墙钟间隔均小于 250 ms；p99 不高于 100 ms，且不出现持续恶化趋势。
5. 每个 D3D12 轮次 RTF 不低于 0.95。若主机资源限制导致低于门槛，必须判为当前平台未通过，不能把慢速仿真的时延外推为实时飞行结论。
6. 120 ms 和 400 ms 故障回归按第 7.3 节产生预期结果。
7. 所有单元、静态和既有回归测试通过，证据清单可从原始日志重算关键结论。

`default` 五轮用于衡量差异和证明问题基线，不要求通过 D3D12 门槛，但不得删除其失败。报告同时给出逐轮结果和配对差值，不能只给平均值。

## 9. 停止与失败规则

- 任何碰撞、围栏越界、旧视觉继续驱动前进、学习策略绕过 PX4 或安全监督器，立即停止本轮并保留证据。
- D3D12 静默回退、冻结配置漂移、日志缺失或哈希不一致使该轮无效；修正后重新开始完整正式序列。
- 任一 D3D12 正式轮未达到 `5/5`、发生正常场景门控、稳定阶段延迟达到 250 ms 或 RTF 低于 0.95，本小节判为未通过。不得用增加轮次稀释失败。
- 若 D3D12 未通过，先报告当前平台和证据边界。下一项候选是相机更新相位调度，但必须作为新的单变量设计，不得在本轮临时叠加。

## 10. 产物与证据等级

版本库提交：

- 本设计、后续实施计划、启动配置与后端证明实现。
- 单元/回归测试、紧凑清单、逐轮摘要、配对比较和最终报告。
- 原始大型日志、ULog、性能数据和轨迹回放的哈希索引。

本机保留但默认不提交：

- 全部 ULog、转发日志、时钟/资源探针、性能采样、轨迹回放和 Gazebo/PX4 控制台日志。

最终报告必须把证据明确标为单元测试、孤立传感器探针、五机 PX4/Gazebo 物理仿真或故障注入。此设计不产生 HITL 或实飞证据，也不完成路线图“真实虚拟相机/IMU → 开源 VIO → PX4 EKF”的实施包 A；它只为该实施包建立可重复、接近实时的五机仿真运行条件。
