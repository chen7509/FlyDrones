# Owned PX4 diagnostic logger staging

The existing sealed physical ULogs contain no `vehicle_odometry`; the fixed PX4 v1.17 logger does not subscribe to it by default. The repository already has an exact, diagnostic-only ten-topic file and byte-level auditor. This stage adds an opt-in route from that fixture to the independent runtime used by an unarmed, declared Agent wire capture. It does not claim an actual PX4 logger selected the file, and it does not change the prior study's workload.

The new `source-diagnostic-v1` option requires the existing execution declaration, runtime binding, wire configuration and owned fixed Agent. Before constructing PX4, the capture revalidates the canonical topic and declaration files, creates `etc/logging/logger_topics.txt` exclusively under its newly created runtime, checks its bytes, and passes `PX4_PARAM_SDLOG_PROFILE=0` only to the owned PX4 child. The execution declaration records the exact source paths and SHA-256; the runtime binding must include both. A post-PX4 cleanup check revalidates the source and copied bytes and fails the capture if either changed. Missing, malformed, linked, already existing or modified inputs fail closed. No existing capture profile opts in by default.

The fixed PX4 `d6f12ad1c4f70ad3230afd7d86e971421e02fef4` (BSD-3-Clause) has `CONFIG_BOARD_ROOT_PATH="."` for SITL; `PX4_STORAGEDIR` resolves from that root. Its `rcS` applies `PX4_PARAM_*` values before `param set-default SDLOG_PROFILE 131`; the fixed logger reads `./etc/logging/logger_topics.txt` in place of defaults. The source hash, exact file format and [official logging explanation](https://docs.px4.io/main/en/dev_log/logging) are in [the earlier diagnostic report](../../PX4_ODOMETRY_SOURCE_DIAGNOSTIC_REPORT.md). The pinned Agent v2.4.3 (Apache-2.0) and ROS 2/`px4_msgs` (BSD-3-Clause), including their maintenance and resource limits, are recorded in the [Agent](../../OWNED_AGENT_CAPTURE_INTEGRATION_REPORT.md) and [typed CDR](../../XRCE_TYPED_ODOMETRY_DIAGNOSTIC_REPORT.md) reports. Reuse these local components rather than introduce a new dependency or reconstruct another logger list.

This is a changed-logging-load development condition. A future study needs a new manifest schema and ID that admits the extra option and declares the source files; current `live-wire-study-v2` intentionally rejects extra fields. Its launch requires the original 4 GiB physical resource gate and no competing processes. After a real run, check the actual logger startup line, ULog dataset/dropouts, Agent/PX4 identity, ROS typed CDR, timestamps/reset, unarmed state, calibrated camera and cleanup. A file copy or matching ULog row alone cannot authenticate the PX4 DDS publisher. Keep `runtime_topic_selection_verified`, `dds_ulog_parity_verified`, `source_authenticated`, fusion and training qualification false in this stage. Never use the diagnostic logging load as evidence that the unchanged five-camera capacity gate passed.
