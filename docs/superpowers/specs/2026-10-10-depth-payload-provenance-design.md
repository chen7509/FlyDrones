# Opt-in raw depth payload provenance for the unarmed capture

The existing 25-second OpenVINS study saved RGB pixels and per-frame depth metadata, but no depth pixels. It cannot support a reproducible EGO observation or prove which obstacle image a future teacher saw. This change adds a prospectively declared, disabled-by-default raw depth sidecar to the current sensor journal. It does not turn the old study into a teacher run, feed a planner, or change VIO/PX4 input.

## Source and choice

The installed Gazebo Sensors 8.2.2 interface is represented by pinned Apache-2.0 source [`RgbdCameraSensor.cc` at `9348f9f`](https://github.com/gazebosim/gz-sensors/blob/9348f9fe8a11b9d50381819f51e17e136aedab8a/src/RgbdCameraSensor.cc): it publishes a `gz.msgs.Image` with the capture stamp, `R_FLOAT32`, row step and raw float32 depth buffer; clipped pixels may be infinite. Earlier repository research recorded a nonarchived upstream and a 2026-10-02 push, but did not prove installed package patches identical. The existing Python Gazebo message binding and single `CaptureWriter` thread are already loaded by the physical harness, so this option adds no runtime dependency; expected storage is about 19.2 MB of raw depth for 250 frames plus protobuf overhead. The adaptation cost is the additional 10 Hz copy/write, event-hash and audit path, which must be measured in any future physical run. Keeping only metadata is rejected because pixels cannot be reconstructed. Converting immediately to a normalized depth array is rejected because it would discard the exact source bytes and invalid-pixel representation. The separate, pinned EGO planner remains unchanged.

## Data and failure contract

An explicit `--record-depth-payload` option is legal only with the existing execution declaration, runtime binding and source fan-out. The execution contract binds the option before startup; legacy runs have the same contract bytes and no sidecar. Each depth callback validates `160×120`, step 640, pixel format 13 (`R_FLOAT32`), 76,800 data bytes and a bounded serialized protobuf. It hands an owned protobuf byte copy to the single writer. These are source-format checks, not metric-depth or camera-calibration qualification.

The writer rejects a linked or invalid depth directory before opening `depth-messages/<sample_ns>.pb`, creates each file exclusively, checks short write/flush/close failures, records exact size/hash/path in the depth event and includes it in a write-once depth manifest. The existing fan-out sees the same event identity and verifies sidecar bytes/hash but receives no depth payload; only the existing IMU/RGB/CameraInfo data enters OpenVINS. A malformed callback latches writer failure and prevents subsequent delivery; an already active delivery may complete before that latch returns. All partial files and error records remain evidence. A finished manifest must have strictly increasing stamps, reconcile every depth event, reject undeclared files, and verify each in-root regular sidecar's declared bytes/hash. These checks do not promise protection against a hostile process racing filesystem path changes. No `fsync` or atomic crash durability is claimed.

## Verification and limits

Pure tests first fail on the absent opt-in, then cover a valid sidecar, disabled legacy behavior, wrong type/step/data length, oversized protobuf, short write/close, duplicate/changed/path-escape sidecars, fan-out identity and declaration drift. Run focused capture/contract/fan-out regression, changed-file Ruff and diff checks; retain RED/GREEN and independently review the result. A future separate physical study must freeze the same 25 s / 1 ms / 250 Hz / 10 Hz 160×120 load and measure its own performance; this implementation does not claim that past VIO, 5-aircraft RTF, PX4 fusion, EGO trajectory, training or flight passed. A later converter may parse the raw protobuf and pair it with a nontruth state and calibrated pose, but it is outside this change.
