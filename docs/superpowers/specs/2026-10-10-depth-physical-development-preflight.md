# Single-aircraft raw-depth physical development preflight

## Intent and evidence boundary

Prepare one fresh, unarmed 25-second PX4/Gazebo/OpenVINS development run with the new raw-depth sidecar enabled. Its purpose is to measure whether the real capture path retains each Gazebo depth protobuf beside the existing RGB/IMU/CameraInfo and safety evidence under unchanged load. This is not an EGO teacher, a student corpus, VIO-to-EKF2 fusion or a five-aircraft capacity pass.

Reuse the fixed successful estimator-aware source study and existing `openvins_health_physical_preflight`/single-attempt executor rather than create a simulator or controller. The input study must have its original qualified physical audit bound by hashes to that study and frozen 25 s, 1 ms physics, 250 Hz raw IMU, 10 Hz 160×120 RGB-D, supported-ready motion, motion-intent, source fan-out and safety contracts. Relative to the source study, the prepared run also selects the existing health-enabled OpenVINS binary/profile and a fresh development seed. The only **new capture option** is `record_depth_payload=true`; no geometry, trajectory, sampling or threshold changes. These simultaneous estimator/seed differences mean this single run cannot isolate the performance cost of depth recording. A matched no-depth control would be required for that causal comparison. Bind the exact capture script, interpreter, code and source audit in the prospective runtime binding. Use a new destination, with no held-out/test-set data. Reject missing source, ambiguous paths, occupied resources and preexisting output; retain any partial preparation failure rather than overwrite.

## Execution and grading

The prepared study uses the existing one-attempt `execute_openvins_health_physical_run` entry and exact declared command; preparation must not spawn PX4, Gazebo, OpenVINS, Docker or training. The execution step must separately verify resource availability, including host memory, before dispatch. The existing generic executor's process check is not a memory qualification, so preparation alone never authorizes launch. No current physical run is started while host free physical memory is below the already frozen 900,000 KiB ROS build reserve; that reserve is used as a conservative *precondition*, not as a physical performance gate.

After a future run, grade it with all original VIO/safety/ULog criteria plus exact depth manifest/event/sidecar reconciliation, observed count and RGB/depth sample pairing, writer latency, queue occupancy and real-time factor. Keep all failed/partial runs. Do not infer metric depth calibration from format checks or use Gazebo truth as a controller input. The fixed Gazebo Sensors 8.2.2 [upstream RGB-D source](https://github.com/gazebosim/gz-sensors/blob/9348f9fe8a11b9d50381819f51e17e136aedab8a/src/RgbdCameraSensor.cc) is Apache-2.0 at `9348f9f`; installed patches remain unverified. Its existing callback/`gz.msgs.Image` interface has no new dependency. The 10 Hz raw sidecar adds about 19.2 MB for 250 frames plus protobuf/log overhead and must be measured rather than assumed free.
