# 100 机分布式任务智能体设计规格

日期：2026-09-21

## 目标

在现有“一机一进程、UDP 邻机通信”基础上增加任务层。地面任务站只发布一次结构化任务；任务被机群接受后，即使任务站关闭，100 个智能体仍能自行分工、重新分配失败节点的工作、执行局部规划并完成集合。地面站不产生逐机航点、速度、姿态或电机指令。

真实飞行器仍需在每架机上保留小型本地控制板。该控制板负责姿态稳定、电机混控、解锁和失控保护；任务智能体只输出受限的位置或速度意图。第一阶段完全在计算机内验证任务自治，继续使用现有运动学多进程试验和 PX4/Gazebo SITL，不要求用户已经拥有硬件。

## 设计选择

采用增量式 Python 任务智能体，不在本阶段整体迁移 ROS 2，也不依赖 Crazyswarm2。原因是现有代码已具有独立进程、局部策略、PX4 适配器和真实 UDP 传输；在其上增加任务层可以直接复用已经验证的控制路径，并保持以后替换为 PX4 ROS 2 接口的边界。

任务分配使用可审计的共识竞价机制，设计形态参考 Consensus-Based Bundle Algorithm（CBBA），但实现仅包含本项目需要的单任务认领、租约、冲突消解和失败接管，不引入完整机器人中间件。学习策略可为任务估价和局部导航提供建议，但不能绕过确定性的安全规则。

## 系统边界

### 地面任务站

任务站只执行以下操作：

1. 将人类任务转换为经过模式验证的 `MissionContract`。
2. 广播任务合同，直到达到规定的接收确认比例。
3. 显示智能体自行上报的只读进度和最终报告。

任务站不得维护用于控制的全局实时位置表，不得决定某个工作单元属于哪架无人机，也不得在任务期间向单机发送航点或避碰指令。任务站关闭必须是正式故障注入项目。

### 机载任务智能体

每个智能体拥有独立进程、独立本机状态、独立任务账本和独立 UDP 端点，并包含六个组件：

- `MissionInterpreter`：验证任务合同，确定性地展开工作单元。
- `TaskAllocator`：计算本机投标，处理邻机投标，通过版本和确定性排序消解冲突。
- `TaskLedger`：记录任务状态、当前获胜者、租约期限和完成证据。
- `LocalPlanner`：把当前工作单元转换为受限导航意图，调用已有学习策略和本地障碍感知。
- `SafetySupervisor`：强制执行速度、地理围栏、机间距、电量和传感器新鲜度约束。
- `FlightAdapter`：在模拟中积分本机运动状态；以后向本机控制板发送位置或速度设定值。

父进程只创建进程、提供不可变场景和同步开始信号，并在所有进程退出后汇总文件。它不能在任务运行期间读取状态后产生控制动作。

## 任务合同

`MissionContract` 使用带版本的 JSON，并在所有智能体启动前完成严格校验。第一版字段如下：

```json
{
  "schema_version": 1,
  "mission_id": "forest-search-001",
  "mission_type": "search_confirm_rally",
  "area_polygon_m": [[0, 0], [200, 0], [200, 150], [0, 150]],
  "search_cell_size_m": 20,
  "target_classes": ["person"],
  "confirmation_quorum": 2,
  "rally_position_m": [220, 75, 20],
  "deadline_s": 600,
  "safety": {
    "maximum_speed_mps": 8,
    "minimum_separation_m": 3,
    "geofence_margin_m": 5,
    "minimum_battery_return_pct": 30
  }
}
```

合同不得包含每架无人机的航点列表。自然语言任务必须先在地面端转换为上述有限结构，并通过模式、范围和安全约束校验；自然语言或大模型输出不能直接进入飞行控制链。

第一版仅支持 `search_confirm_rally`。它确定性地产生以下工作单元：

1. `search_cell`：搜索一个网格区域。
2. `confirm_detection`：由另一架无人机确认一个候选目标。
3. `relay`：在局部网络分区边界维持消息转发，仅在连通性不足时产生。
4. `rally`：任务截止或搜索完成后前往集合区。

## 分布式分配与共识

每架无人机只依据任务合同、本机位置、电量、能力、现有负载和邻机消息计算投标。投标包含预计完成时间、能耗代价、能力匹配和任务切换代价。比较采用固定字段顺序；分数相等时较小 `vehicle_id` 获胜，保证所有节点最终得到同一结果。

每个任务记录：

- `task_id` 和不可变任务内容哈希。
- 当前获胜者、投标值和分配版本。
- 获胜者最后一次租约续期时间。
- `open`、`claimed`、`active`、`completed` 或 `failed` 状态。
- 完成证据哈希和确认者集合。

认领租约必须周期续期。邻机超过 `lease_timeout_s` 未收到续期后可重新竞价；旧获胜者恢复通信时，以更高分配版本和确定性冲突规则为准。完成状态只前进不后退。搜索任务只需一个执行者；目标确认必须由合同规定数量的不同无人机提供独立证据。

第一版固定 `lease_timeout_s = 3.0`，活动节点每秒续期两次，竞价与账本合并频率为 5 Hz。故障节点任务最迟在租约超时后的下一个竞价周期重新开放。

网络分区期间，各分区可继续执行已经认领的任务。分区合并后，重复认领通过版本、投标和 `vehicle_id` 顺序消解；已经产生的重复观测可以作为证据保留，但只计一次任务完成。

## P2P 消息协议

现有位置/速度 UDP 数据报继续用于短周期避碰，并增加第二类带版本任务消息。两类消息使用不同魔数和独立序列号，防止错误解码。

任务消息类型包括：

- `mission_accept`：接受任务合同及其哈希。
- `bid`：一个或多个任务的本机投标。
- `award`：本机账本中的当前获胜者和版本。
- `lease`：活动任务租约续期。
- `progress`：有限频率的进度摘要。
- `evidence`：发现或完成证据的元数据与哈希。
- `health`：能力、电量和降级状态摘要。

消息必须包含协议版本、任务 ID、发送者 ID、单调序列号和负载校验。无效版本、未知发送者、非有限数值、过期序列和错误任务哈希必须被拒绝并计数。大型图像不通过群体 UDP 广播；只广播证据摘要，原始数据保存在本机或按需传输。

100 机时禁止持续全网全播任务消息。位置消息只发给配置的近邻或通信范围内节点；任务消息通过确定性的八邻居覆盖网转发，邻居偏移为 `±1、±3、±7、±13 (mod N)`，并使用周期反熵摘要。故障和分区试验通过过滤覆盖网边来模拟，而不向父进程暴露状态。单个任务数据报不超过 1200 字节；每个智能体每秒最多发送 10 个任务数据报，进度摘要最多 1 Hz，确保任务层不会挤占 10 Hz 或更高频率的本地控制循环。

## 智能体状态机

每架无人机独立运行：

`BOOT → WAIT_MISSION → AUCTION → TRANSIT → EXECUTE → VERIFY → AUCTION/RALLY → LAND`

同时存在独立的安全状态：

`NOMINAL → DEGRADED → RETURN/LAND → EMERGENCY`

任务状态不能覆盖安全状态。安全监督器进入 `RETURN/LAND` 后，任务层释放未完成租约并停止竞价；进入 `EMERGENCY` 后仅允许执行本机控制板定义的紧急行为。

任务完成、截止时间到达或可完成任务为空时，每架机根据本机账本进入集合状态，不依赖“中央宣布结束”。合同规定的完成比例通过邻机完成摘要逐步收敛。

## 学习与确定性安全边界

学习模型可以：

- 评估本机执行某任务的成本。
- 从深度感知和目标方向生成局部导航建议。
- 对搜索路径或确认位置排序。

学习模型不能：

- 直接输出电机 PWM、姿态率或解除安全限制。
- 改写任务合同或提高速度、降低间距和降低返航电量阈值。
- 宣布任务完成而不提供满足模式要求的证据。

`SafetySupervisor` 在学习输出之后执行，限制速度和加速度，拒绝越界意图，处理过期深度帧，并复用现有 UDP 邻机轨迹进行预测避让。真实硬件阶段由本地控制板继续承担姿态稳定和 Offboard 失联保护。

## 故障处理

必须覆盖以下故障：

- **任务站退出**：已接受任务继续运行，中央实时控制计数保持零。
- **单机进程退出**：其租约过期，邻机重新竞价；其他进程不退出。
- **最多 10 架智能体失效**：遗留搜索单元在 3.2 秒内重新开放竞价，并在 5 秒验收期限内被存活节点接管。
- **网络分区与恢复**：分区内继续工作，恢复后账本收敛并消除重复认领。
- **邻机数据过期**：从本地缓存删除，规划增加保守间距。
- **深度数据过期**：最后深度帧超过 0.5 秒时立即停止前进；保持 2 秒仍未恢复则进入本机降落状态。
- **定位异常或越界**：停止任务并进入返航/降落，不把异常位置传播为可信状态。
- **低电量**：释放任务，广播健康降级并返航；任务由其他智能体接管。
- **消息洪泛或畸形消息**：限流、拒绝、计数，不阻塞控制循环。

## 模拟场景

第一阶段实现一个 100 机森林搜索场景。区域划分为至少 100 个搜索单元，并在运行中注入候选目标。所有智能体收到同一合同，自行认领搜索单元；发现目标后产生确认任务，达到两机确认后进入已确认状态，最终在森林外集合。

场景提供以下确定性故障组合：

1. 任务发布后关闭任务站。
2. 运行中随机终止 10 个智能体进程。
3. 将通信图分成两个分区，再恢复连接。
4. 注入延迟、抖动、随机丢包和全网短时断联。
5. 注入一个低电量节点和一个深度传感器冻结节点。

随机源按任务 ID 和试验种子固定，保证失败可重现。

## 验收标准

100 进程端到端试验必须同时满足：

- 任务站关闭后仍继续推进任务，中央航点、速度和避碰命令数均为零。
- 使用 100 个不同操作系统进程；每个进程只拥有一个智能体状态和 UDP 端点。
- 至少 95% 的搜索单元在截止时间内完成。
- 所有注入目标均达到两架不同无人机确认。
- 10 架智能体失效后，其活动任务在 5 秒内重新开放，并最终被存活节点接管。
- 网络恢复后 5 秒内，所有存活节点对任务获胜者和完成状态收敛。
- 同一任务最多有一个有效获胜者；重复执行只记录一次完成。
- 物理碰撞为零，最小机间距不低于合同限制。
- 所有存活智能体抵达集合区或执行了明确的安全返航/降落。
- 畸形、过期和错误任务消息均被拒绝，控制循环没有因任务消息阻塞。
- 报告给出任务完成率、重分配延迟、共识收敛时间、消息率、丢包、避让和失败恢复指标。

验收器必须从各进程退出后写出的独立日志重新计算任务所有权、完成比例、进程 ID、通信来源和轨迹间距，不能只相信智能体自己上报的汇总值。

## 文件边界

- 新建 `src/flydrones/mission_contract.py`：任务模式、严格验证和工作单元展开。
- 新建 `src/flydrones/task_consensus.py`：投标、租约、版本和冲突消解。
- 新建 `src/flydrones/task_udp.py`：任务消息编码、验证、限流和邻接传播。
- 新建 `src/flydrones/mission_agent.py`：单智能体状态机与现有导航/安全接口组合。
- 新建 `src/flydrones/mission_stress.py`：100 进程任务场景、故障注入和离线验收。
- 新建 `tools/run_mission_swarm.py`：启动任务发布器和独立智能体进程。
- 新建相应测试文件，分别覆盖合同、共识、UDP、状态机和多进程验收。
- 生成 `results/mission-swarm-100/` 中的逐机日志、汇总 JSON、中文报告和轨迹/任务图。

现有 `peer_udp.py` 继续负责高频邻机运动状态；任务消息不堆入该文件。现有 `distributed_px4.py` 在第一阶段保持不变，避免任务层试验影响已通过的五机 PX4 验收。

## 开源参考与采用范围

- PX4 ROS 2 Interface Library：保留为后续真实硬件适配方向；部分接口仍为实验性，本阶段不作为运行依赖。<https://docs.px4.io/main/en/ros2/px4_ros2_interface_lib>
- PX4 `px4_ros_com`：后续可用于 ROS 2 与 PX4 消息桥接，本阶段继续使用已有 MAVLink/PX4 适配器。<https://github.com/PX4/px4_ros_com>
- Crazyswarm2：参考大型群体的命名和启动模式，不引入其 Crazyflie 专用运行栈。<https://github.com/IMRCLab/crazyswarm2>
- CBBA/CBAA：采用其“局部投标加共识”的思路；第三方示例仅作算法参考，不直接复制未验证实现。<https://github.com/lucatrevisanii/multi-robot-coordination>

## 已知边界与后续阶段

第一阶段的 100 机试验仍是单计算机上的多进程运动学模拟。它能验证任务自治、消息规模、失效接管和控制路径去中心化，不能证明真实无线网络容量、视觉识别准确率或 100 架飞行器的空气动力安全。

通过后按顺序进入：五机 PX4/Gazebo 全物理任务试验；两块无桨 Pixhawk 的 HITL 台架；两机系留低速试验；五机封闭场地试验。扩大真实机数必须由上一阶段的碰撞、失联、急停和任务恢复验收结果决定。
