# Fixed EGO teacher causal provenance design

## Intent and present boundary

The goal is a verifiable teacher label from the real pinned EGO-Swarm planner, paired with the deployment-visible PX4/camera observation that was available to that planner. The existing bridge's `reference.sim_ns` means only "latest observation at command receipt"; the v3 recorder verifies equality with the student frame but cannot infer upstream input causality from that equality. The old synthetic smoke and comparison archive stay immutable. No result may enter a new training corpus merely because the socket response followed an observation packet.

The pinned upstream is `ZJU-FAST-Lab/ego-planner-swarm@23a8d5a191711dd65633df689bd00f55d4dea8f9`, GPL-3.0. The inspected ROS 2 code uses asynchronous odometry, synchronized image/pose, a separate occupancy-update timer, planning/replanning and a 10 ms trajectory-server timer. The EGO-Swarm [paper](https://arxiv.org/abs/2011.04183) likewise describes an asynchronous architecture, but source code, not the paper, defines this pinned implementation. The source snapshot for the five relevant implementation/message files is Git-blob and SHA-256 verified in `results/ego-causal-provenance-dev-1701/source-manifest.json`.

## Findings that shape the interface

- `ego_replan_fsm.cpp:249-257` consumes odometry position and velocity without retaining `msg->header.stamp`. Its `callReboundReplan` publishes a `Bspline` with `start_time` and `traj_id` (`799-824`), without the odometry or depth image identity.
- `ego_replan_fsm.cpp:643-645` obtains the first local start state from odometry; `672-674` samples an earlier trajectory for replanning. The latest odometry callback is therefore not always the start-state source. Diagnostic records must distinguish these paths and bind a prior trajectory session/ID and sample instant when applicable.
- `grid_map.cpp:758-791` accepts a synchronized image and pose and sets a pending map update flag; `updateOccupancyCallback` applies the depth image later (`709-756`). The inspected callbacks do not carry an applied image identifier to the planner trajectory message. Receipt of an image is therefore not proof that a particular plan used it.
- `traj_server.cpp:27-68` copies `Bspline.start_time`/`traj_id`; `163-172` samples a separate clock; `209-231` publishes `PositionCommand` with that trajectory ID and a current clock stamp. `Bspline.msg` declares signed `int64 traj_id`, the trajectory server stores it in C++ `int`, and `PositionCommand.msg` declares unsigned `uint32 trajectory_id`. A lossless link requires `1 <= raw_id <= INT_MAX`, equality across all three representations, and uniqueness within a session; otherwise narrowing/wrap can alias plans. Neither message contains an input observation identifier.
- The official [ROS 2 Humble Odometry definition](https://github.com/ros2/common_interfaces/blob/humble/nav_msgs/msg/Odometry.msg) places twist in `child_frame_id`; the pinned FSM directly treats numeric `twist.twist.linear` as world velocity. A future comparison must declare and test this EGO-specific input convention at nonzero yaw, or use a separately versioned upstream compatibility patch with numerical parity evidence. It must not silently call the current message standard body-frame odometry.

## Selected approach and alternatives

Keep the pinned algorithm and original performance evidence untouched. Build a separately versioned, minimal diagnostic-instrumentation variant that records the input snapshot used at plan creation and publishes it with a session-qualified trajectory ID. The diagnostic must observe the actual planner and occupancy state without feeding truth or changing trajectory optimization. A small bridge-side verifier will match `PositionCommand.trajectory_id` to the instrumented plan record and to real odometry and *applied* depth/pose events. It will distinguish a valid ongoing control reference from a fresh teacher label. Only the latter can be written to a new corpus, and only after the matched PX4 EKF2/camera producer passes its own source, calibration, timing and safety gates.

Rejected alternatives: matching by `PositionCommand.header.stamp` or by bridge receipt order cannot establish input consumption; `trajectory_id` alone names a plan, not its inputs. Restarting the planner for each observation would erase the map and change the algorithm. Replacing the upstream planner with a local imitation would defeat the baseline.

## Diagnostic record and fail-closed rules

Each run uses an immutable run/session identifier. The input journal records exact observation sequence/sim time, PX4 odometry sample and clock epoch, camera sample, image digest, calibration digest, and the producer process identities. Instrumentation records the last consumed odometry sample and the map revision plus the depth/pose frame that was actually *applied* before plan generation. A plan record binds those fields to `trajectory_id` and plan start time in one planner session. The verifier accepts a plan-to-command ID link only for positive raw IDs at most the target C++ `INT_MAX`, after exact equality of the raw `int64`, stored `int` and emitted `uint32` values and uniqueness within that session. The bridge records raw `PositionCommand` trajectory ID, header stamp and arrival monotonic time, retaining duplicates, aliases, old-plan output, missing-map cases and failures.

The verifier refuses session changes, counter reuse, missing records, out-of-order timestamps, stale odometry or map revisions, image delivery without occupancy application, mismatched camera/odometry sources, unknown calibration, corrupted hashes and any truth-source input. A command from an older valid trajectory may remain a baseline control action if the ordinary controller safety gate accepts it, but it is **not** a newly attributed teacher target for the current frame. A new corpus sample requires a source-attested student observation and a planner record whose applied map includes the required input history; the record must state the history window, rather than falsely claiming the planner used only one RGB-D frame.

## Validation and rollout

First seal this static source audit. Then implement the diagnostic patch and verifier with synthetic normal/late/reordered/reset/fault tests; build a new image with upstream commit, patch, message/type-support and binary hashes. On development scenes, compare patched and unpatched trajectories under the same input and reject any material planning difference before using the patched variant as a baseline. Only then run an owned, resource-gated single-drone ROS development capture with raw journals and ULog, never on the held-out set. Freeze the exact profile before new random held-out trials. Source attestation, teacher causality and fair-performance qualification remain independent booleans. No PX4/Gazebo run is implied by this document.

## Diagnostic clock and bridge reconciliation amendment (2026-10-11)

The first static candidate has map/plan ordering within the planner process, but no recorded node-clock time at either completion. Its independent depth-receive sequence cannot be treated as the bridge observation sequence. A separately versioned candidate must record the node clock at completed occupancy application and successful plan publication, plus a steady-clock event stamp for latency analysis. These are *node-clock* values until a frozen launch and runtime `/clock` record proves `use_sim_time` was active; neither `Bspline.start_time` nor a `PositionCommand.header.stamp` may substitute. The bridge must journal the exact serialized ROS image, pose, odometry and received command bytes, their digests, original source identity, session, and actual publish/receive order. A later adapter may map independent sequences only through exact bytes and times, rejecting ambiguous repeated hashes, skipped/unknown cloud writes, an unbound depth-odometry extrinsic, clock regressions, incomplete journals and mismatched process sessions. The existing offline join's equal map/odometry/observation sequence rule is intentionally conservative, not evidence that EGO's asynchronous paths share one sequence. Any broader history-aware join requires its own explicit schema and tests before eligibility can change; synthetic matches continue to return `teacher_qualified=false`.

The first offline adapter accepts only a proposed, source-attested bridge message schema and complete diagnostic journals from one planner PID and one trajectory-server PID. It requires the bridge message digest to appear uniquely for depth, camera pose, odometry, B-spline and command at the expected steps; it checks continuous per-process journal sequence, same run/session, completed map revision before the plan, unchanged map during planning, no cloud mutation, lossless positive trajectory IDs, same-session prior-trajectory lineage and nondecreasing steady clocks. It refuses an odometry-pose depth route until extrinsic identity is captured. A matching synthetic bundle returns `teacher_qualified=false` and `runtime_source_verified=false`: acceptance of the proposed record schema is not evidence that a real ROS publisher/receiver produced those bytes or that the planner's output is numerically unchanged. The producer and runtime parity gates remain separate.
