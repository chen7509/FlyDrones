# Fixed XRCE-to-typed-odometry diagnostic design

## Purpose and boundary

Prove or falsify a **synthetic** single-message path from the pinned Micro-XRCE-DDS Client through the newly rebuilt Agent to the existing pinned ROS 2 `px4_msgs/msg/VehicleOdometry` collector. This is an interface diagnostic. It does not authenticate a PX4 process, provide camera/VIO data, qualify EKF2 fusion, or admit training data. Never start PX4, Gazebo, OpenVINS, a trainer, or a network-facing Agent in this study.

Reuse its sealed runtime bundle SHA-256 `4279d999c02836e3f7076e948d2e92aefcc08bf62ea8c0e3e597dde2896c3262` and fixed Humble image `sha256:a4dae62b38bc01a01d084be7b68db83ec804fef7673604e1a9c986a4baa88a6a`; do not substitute a current branch or old WSL binary. The pinned client source and prior generated install are already local, so no download is needed.
- PX4 `d6f12ad1c4f70ad3230afd7d86e971421e02fef4` and `px4_msgs` `148bdb4b8214a4d8de83029777fe8d334c74db6f` are BSD-3-Clause. The actual fixed PX4-generated `dds_topics.h` specifies `px4_msgs::msg::dds_::VehicleOdometry_`; fixed `utilities.hpp` turns `/fmu/out/vehicle_odometry` with message version 0 into DDS topic `rt/fmu/out/vehicle_odometry`, using best-effort, transient-local, keep-last writer QoS. Do not infer these strings from current `main` alone. See [fixed PX4 template](https://github.com/PX4/PX4-Autopilot/blob/d6f12ad1c4f70ad3230afd7d86e971421e02fef4/src/modules/uxrce_dds_client/dds_topics.h.em) and [official XRCE guide](https://docs.px4.io/main/en/middleware/uxrce_dds).

The collector is read-only and retains `eligible_for_live_capture=false`.

## Study design

Create a small, explicitly synthetic C client that uses pinned `uxr/client/client.h` calls to open UDP on loopback, create a session, participant, topic, publisher and datawriter by **binary** entity creation, check each returned status, and publish the frozen body once after bounded discovery time. Its object IDs and QoS follow fixed PX4 `utilities.hpp`; use a dedicated test client key and UDP port, with no PX4 source claim. Compile this diagnostic against the pinned installed XRCE Client and Micro-CDR inside the same Humble image, offline, single-job, with source and binary hashes. The custom harness is test code, not the complete PX4 client.

Require at least 1.5 GiB host free physical memory and no competing Docker/PX4/Gazebo/OpenVINS/training process immediately before launch; this diagnostic threshold does not change the separate 2 GiB offline-build or 4 GiB physical-simulation gates. Run the Agent, existing typed collector and diagnostic client in one owned Docker container with `--network none`, read-only artifact/source mounts, at most 1 CPU/768 MiB/128 PID and a 30-second outer deadline. Start the collector before the client; require actual Agent `running` evidence before proceeding. Bind UDP to the container loopback and use a unique nonproduction port. Every process is an owned child with explicit PID, timeout, termination/kill result and final container absence; do not infer delivery from `sendto` or publisher exit alone. At normal completion require XRCE session/entity status, the Agent's corresponding client/entity evidence, exactly one complete typed collector sample, independent CDR and all-field parity, and matching frozen image/binary/source hashes. A synthetic GID can only label this test; it cannot authenticate PX4.

Fail closed on changed bundle, source, collector binary, generated message or CDR; missing/malformed payload; wrong topic/type/version/QoS; absent Agent; status failure; timeout; incomplete or duplicate journal; CDR mismatch; process cleanup failure. Preserve each attempt and original logs. A failed first attempt is not silently retried or reclassified. If a concrete harness issue is corrected, use a new versioned evidence directory and keep the original.

## Alternatives and next gate

The unmodified upstream HelloWorld example would verify a session but not the already built PX4 type collector. Starting full PX4/Gazebo would consume a separate 4 GiB physical gate and confound transport with dynamics. The fixed synthetic client is the narrowest end-to-end contract check. Even if it passes, the next study must bind a **real, unarmed PX4** XRCE publisher to Agent process identity, DDS GID, clock/reset, ULog, calibrated camera and safety health in one frozen physical episode. The v10 TIMESYNC and five-camera 0.873 RTF failures remain independent.

## Development amendments after preserved attempts

The first complete synthetic callback (v3) was not repeatable: v4 and v6 received no collector sample. A five-poll ROS graph gate in v6 proved type/QoS-visible publisher and collector endpoints but did not prove data delivery. v5 had a separate Humble API shape failure before sending. Verbose Agent evidence in v7 shows the exact 116-byte body entering the Agent and a DDS `DataWriter::write`, while the CycloneDDS collector still recorded zero messages. Therefore the remaining observed gap lies after Agent DDS write and before the collector callback; no PX4 or fruit-fly algorithm was involved.

One further **independently named development profile** may run the same Agent, client, CDR, graph gate and collector with ROS 2 `rmw_fastrtps_cpp` instead of `rmw_cyclonedds_cpp`, both present in the frozen Humble image. This tests whether the mixed DDS implementation contributes to the one-shot delivery gap. It does not reclassify failed CycloneDDS attempts or authorize a live PX4 source. Preserve callback absence and cleanup as a valid failure, and do not retry the identical profile until new evidence gives a reason.
