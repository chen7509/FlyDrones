# PX4 ULog odometry topic availability preflight

The next owned PX4/Agent source trial needs independent evidence that its ROS 2 `VehicleOdometry` samples came from the intended PX4 estimator. A DDS publisher GID identifies a middleware endpoint, but the [Micro XRCE-DDS Agent](https://github.com/eProsima/Micro-XRCE-DDS-Agent) creates DDS entities on behalf of an XRCE client; a GID or caller-provided run label alone cannot identify the PX4 process. A field-level ULog cross-check is one additional prerequisite, not source authentication by itself.

This stage inspected two already sealed, successful unarmed physical runs without launching a simulator, Agent, ROS node or training process. The installed WSL `pyulog` 1.2.4 parser (existing dependency, [BSD-3-Clause](https://github.com/PX4/pyulog/blob/main/pyproject.toml), upstream non-archived with 2026 activity observed) read each original ULog. A small read-only preflight checks whether one instance-zero `vehicle_odometry` dataset contains the fixed [PX4 `d6f12ad` message](https://github.com/PX4/PX4-Autopilot/blob/d6f12ad1c4f70ad3230afd7d86e971421e02fef4/msg/versioned/VehicleOdometry.msg) scalar and array fields with consistent lengths and monotonic timestamps. It never grants live capture, fusion, training or flight. The initial CLI attempt failed because importing the training package required `torch`, which is absent in WSL; the failure was retained, and the final read-only CLI loads this isolated standard-library preflight module directly.

The exact counts, source paths, parser version and hashes are in `results/px4-ulog-odometry-preflight-dev-1701/audit-v2.json`. Both ULogs contain 84 dataset instances. The final CLI prints structured refusal evidence and exits **1** when a required odometry topic is absent. This **contradicts** any claim that the old ULogs can directly cross-check every DDS `VehicleOdometry` field. Related attitude and local-position topics support a weaker estimator-consistency check, but they are not the same serialized odometry sample.

The fixed PX4 logger source `src/modules/logger/logged_topics.cpp` at commit `d6f12ad1c4f70ad3230afd7d86e971421e02fef4`, local SHA-256 `33c1cd7c55dc81d4fa53153b7f269401b67c7f6edc929707ec536203096bcfe5`, includes `vehicle_attitude` and `vehicle_local_position` in its default list but no `vehicle_odometry`. It reads `PX4_STORAGEDIR/etc/logging/logger_topics.txt` and chooses that list **instead of** the configured defaults when the file supplies topics. The [PX4 logger documentation](https://github.com/PX4/PX4-Autopilot/blob/main/docs/en/dev_log/logging.md) confirms the file-based override. Therefore a future study cannot simply add a one-line topic file and claim the original logging/evidence load remained unchanged. It must prospectively freeze a complete topic list, verify its runtime selection and account for added logging load, or use a separately justified weaker check.

Independent review found that malformed non-time values could pass the schema candidate, and that the CLI returned success on missing topics. Two failing regression tests reproduced these paths; the final code rejects malformed numeric/frame/reset values and returns nonzero on refusal. Six focused tests pass; the earlier four-test result and original real audit remain retained. A complete schema candidate still has `eligible_for_live_capture=false`; nonfinite fields may remain as typed PX4 unknowns, and no DDS/ULog value comparison has run. The next source study still requires the previously pending generated-type synthetic DDS/CDR parity, a pinned Agent executable, owned PX4/Agent process and isolated-domain evidence, clock/reset mapping, actual ULog odometry samples, EKF2 health and calibrated camera before any training-data grant. The older successes and failures remain unchanged.

The first evidence-seal invocation left an incomplete archive because the empty diff-check output file did not yet exist. That partial file and its hash are retained separately in `results/px4-ulog-odometry-preflight-dev-1701`; the final archive prechecks all members before creation and verifies every member SHA-256 and ZIP CRC.
