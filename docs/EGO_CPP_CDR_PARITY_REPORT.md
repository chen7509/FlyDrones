# EGO 命令 CDR 的 C++/Python 一致性核验（2026-10-12）

固定镜像 `sha256:a4dae62b38bc01a01d084be7b68db83ec804fef7673604e1a9c986a4baa88a6a` 中，用安装的 ROS 2 Humble `quadrotor_msgs/msg/PositionCommand` 类型支持编译并运行了独立的 `rclcpp::Serialization` C++ 探针。它使用此前同进程 DDS 回环的相同字段，得到 **169 字节**规范 CDR，SHA-256 `667b1a4afa5778e53947cc5e5262df9ee41a7e2ccf53703cc960309cf04078a5`，与 Python `rclpy` 发布前的规范字节逐字节相同。所测 CycloneDDS 原始回调是这 169 字节后接三个零字节，共 172 字节，SHA-256 `2612f8666942b9414c1d2f94caea18df02864dc12438fad515e47a250f181d47`。固定镜像的 `rclpy.deserialize_message` 接受该实际回调，并再序列化为同一 169 字节规范形式；解码的时间戳为 9000 ns、轨迹编号 7、状态 1。

这验证了**这一镜像、消息定义和测试字段**的 C++ 类型支持与 Python 规范序列化一致，并验证现有桥接反序列化器能够读入所测 DDS 填充。它没有编译 EGO 只读诊断补丁，没有运行 EGO 规划器，也没有证明任何命令来自特定规划输入、可以作为训练教师或用于安全放行。

探针使用固定镜像、无网络、单容器、768 MiB/1 CPU 上限和独立拥有的容器名；最终 v5 的编译、运行、输出及清理均退出 0，二进制 SHA-256 `4c935181ffafbc3e3550623a028892299241b4261fb53ebbe1d8c76206f07580`。v1 在 Windows 可用内存 1773 MiB、低于预先设定的 1800 MiB 门槛时拒绝，未启动容器；v2 因先启用 Bash `nounset` 与 ROS setup 脚本冲突而失败；v3 因缺 `package.xml` 而在 CMake 阶段失败；v4 编译成功但 `/tmp` 挂载为 `noexec`，执行二进制失败。各失败和改进后的脚本分别保留，没有改写成成功记录。另一个有界容器运行只对已有 DDS 回调字节进行解码，没有启动规划器。

完整 EGO v2 补丁构建仍有独立的 **2500 MiB Windows 可用内存**启动门槛及 1536 MiB Docker 限额。旧试验在 2128 MiB 时拒绝；本阶段再次观察到 1902–2352 MiB，未降低门槛或启动构建。源补丁的 `git apply --check` 已在先前的固定镜像只读探针通过，但不等于编译通过。下一步是资源准入后的单次补丁构建，再用相同开发输入核对原版与诊断版规划数值；这些都不得以本报告的 CDR 结果替代。
