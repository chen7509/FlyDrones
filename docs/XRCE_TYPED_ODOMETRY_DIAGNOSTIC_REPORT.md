# Fixed XRCE-to-typed-odometry synthetic diagnostic

## Result and scope

The pinned Micro-XRCE-DDS Client generated one synthetic `VehicleOdometry` sample through the pinned Agent and the existing typed ROS 2 collector in three separately owned Fast DDS development runs (v8–v10). Each collector wrote exactly one sample and a complete terminal row. The XRCE body at Agent `DataWriter::write`, the collector CDR, all 13 recorded state/scalar fields, and an independent ROS 2 deserialization agree with the sealed v6 synthetic input. The graph observer's publisher GID equals the callback GID. This validates this **synthetic interface condition**, not a PX4 producer or a flight-control path.

Earlier mixed Agent Fast DDS → collector CycloneDDS attempts remain distinct: v3 received one callback, whereas v4, v6 and v7 received none **within their actual observation windows**. The harness supplied a 15-second collector lifetime but could terminate it after a further 10-second wait following client/graph completion; these are not full 15-second negative observations. In v7 the Agent demonstrably accepted the exact 116-byte XRCE body and called DDS `DataWriter::write`; the collector still recorded zero samples in that window. Thus endpoint discovery and Agent write were insufficient to prove callback delivery in that condition. This is evidence of an integration/timing issue in the mixed setup, not evidence that a particular DDS implementation is defective. v5's graph observer exited before sending because the pinned Humble QoS API returned a tuple rather than the shape first assumed.

Every runtime was synthetic, unarmed, offline (`--network none`), and limited to one CPU, 768 MiB and 128 PIDs. The host preflight required at least 1.5 GiB free; v8–v10 recorded 1.91–1.97 billion available bytes. No PX4, Gazebo, OpenVINS, trainer or network ODOMETRY publisher was started. The recorded post-run query found no named container; because preflight/cleanup used Windows `docker` and execution used WSL `docker`, the evidence does not prove they addressed the same daemon. The collector wrote source timestamp, GID, CDR and full decoded state; the graph observer's GID matched. This is **not** a PX4-process/ULog attestation. The launcher intentionally writes `typed_callback_verified=false`; only the separate post-run audit can set its synthetic callback result true. The strengthened audit now checks recorded return codes, actual source/binary/image identifiers and cleanup errors; it explicitly reports `runtime_daemon_identity_qualified=false` for these historical runs. That field cannot be retroactively repaired.

An additional no-Agent refusal probe is preserved: its first setup lacked a required client library and exited 127; corrected v2 was stopped by the five-second outer deadline (124), with no owned container remaining. This proves bounded harness cleanup, but the client itself has no internal no-Agent timeout. Missing/malformed body, nonzero entity status, wrong ready marker, altered journal field and altered Agent client key were separately rejected. Topic/type/version are compile-time constants pinned to fixed PX4 source; an independently built wrong-topic runtime was not executed.

## Verification and limits

- The final v5 client was compiled with C99, `-Wall -Wextra -Werror`; fixed-image `ldd`, `readelf`, topic/type description and 116-byte input check passed. Its ELF was retained byte-for-byte.
- Targeted client plus adjacent collector/journal regression: **60 passed** after review with the repository's `PYTHONPATH=src`; the initial import failure without that path and a first post-review assertion/formatting failure remain in the evidence. Changed-file Ruff passed. A one-off audit altered a decoded field and a client key in separate copies; both were refused. Review then identified incomplete cleanup and preflight checks; these were fixed in the post-run audit and covered by synthetic mutation tests without changing the captured runtime. The graph observer now resets its stability counter on any incompatible poll; that hardening was not part of the v8–v10 executable source and is not retroactively claimed. The client's best-effort session call did not check a delivery acknowledgement; `synthetic_sent=1` is only a local send declaration, and the independent typed callback is the delivery proof.
- The independent pinned-image decoder checked seven arrays and six scalar fields for each successful v8–v10 journal. The audit separately compared 13 fields to the sealed v6 sample, Agent DDS body and graph/callback GID. No stale frame was repeated to manufacture a rate.
- `quality=0`, `reset_counter=0` and the sample geometry come from synthetic v6 bytes, not live VIO health. The current raw IMU noise profile remains uncalibrated in hardware. PX4 publisher identity, TIMESYNC/ULog link, EKF2 innovation, calibrated camera, safety supervisor decision, 5/20-aircraft load, HITL and real flight are **untested here**. Fusion and training eligibility remain false. The earlier first-TIMESYNC deadline failure and five-camera 0.873 RTF below 0.95 remain failures.

Next work should bind a **real unarmed PX4** XRCE session and ROS callback to a single episode's Agent PID, GID, clock/reset evidence and ULog while retaining the full 4-GiB physical preflight and safety gate. The mixed-RMW zero-message attempts require a separate investigation if that deployment combination is needed. No EKF2 injection or flight authorization follows from this synthetic result.
